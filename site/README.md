# The project site

The site on GitHub Pages: <https://3dgep.github.io/vgl/>, to move to `vgl.3dgep.com` (below).
It holds:

- the landing page (`index.html`, `style.css`, `images/`), written by hand without a site
  generator, with the brand's logos, favicons and tokens (`docs/assets/brand`, served at
  `brand/`). It follows the system's light or dark scheme until a visitor picks one with the
  switch in the bar (`theme.js`), which the browser remembers;
- the live demo (`demo/`): the OpenGL sample's page from the `emscripten` build
  (`samples/gl/web`), on the sample packs (`samples/data/packs`) served beside it;
- the API reference (`api/`), generated by Doxygen from the public headers (`Doxyfile`, with
  `api-main.md` as its first page).

The screenshots in `images/` are the OpenGL sample's own check images (`vgl-gl --check --save
<directory>`, logarithmic depth), converted to PNG.

## Building

`.github/workflows/pages.yml` builds and deploys the site from `main` when `site/` changes,
when a release is published, and on a manual run (`gh workflow run Pages`). Locally, with an
`emscripten` build of the OpenGL sample and Doxygen:

```sh
cmake --preset emscripten
cmake --build --preset emscripten-release --target vgl_gl_sample
site/build.sh build/emscripten/bin/Release build/site
python3 -m http.server 8095 --directory build/site
```

and open <http://localhost:8095/>. `site/build.sh` fails if Doxygen warns.

## The demo without headers

The demo runs threads, which browsers allow only in a cross-origin isolated page
(`samples/gl/web/README.md`), and GitHub Pages cannot send the headers for it. So the site's
copy of the page loads `demo/coi.js` first: when the page is not isolated, it registers the
service worker `demo/coi-sw.js` and reloads, and the worker then adds
`Cross-Origin-Opener-Policy` and `Cross-Origin-Embedder-Policy` to the demo's responses.

GitHub Pages also compresses every file type it does not know as already compressed, pack files
included, and answers range requests with ranges of the compressed stream, which no reader can
decode (`vgl-bake check` reports it). So `site/build.sh` gives the site's copies of the packs'
files a `.zip` suffix, a type Pages serves as it is, and the worker sends the demo's reads of
`data/packs/...` to those names, with their `Range` header. The packs are unchanged.

The workflow checks the result with `tests/browser/page_check.mjs --url`, from a server that
sends no headers.

The sample packs are the one set of data the project serves: small, coarse and already in the
repository, for the demo only (design document, section 10.2). Integrators bake and host their
own packs.

## The domain vgl.3dgep.com

Pages deployed by a workflow take their custom domain from the repository's settings, so the
site needs no `CNAME` file. To move the site to `vgl.3dgep.com`:

1. Verify the domain for the organization, so that no other account can claim it: the
   organization's Settings, Pages, "Add a domain", `vgl.3dgep.com`, then the TXT record GitHub
   shows, at `_github-pages-challenge-3dgep.vgl.3dgep.com`.
2. Add a CNAME record for `vgl.3dgep.com` pointing at `3dgep.github.io`.
3. Set the custom domain in the repository's Settings, Pages, or with
   `gh api -X PUT repos/3dgep/vgl/pages -f cname=vgl.3dgep.com`, and turn on "Enforce
   HTTPS" once GitHub has issued the certificate.

`3dgep.github.io/vgl` then redirects to the new address. The site links to itself relatively,
so nothing in it changes.
